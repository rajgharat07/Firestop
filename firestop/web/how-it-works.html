How it works

Compromise in. Paths out. Seal the rest.

Firestop is not “N packages affected.” It answers with concrete exposure paths and the fewest dependency bumps that cut every one of them — resolved as of a moment in time.

Scroll the steps — the pipeline highlights as you go.

01

Name the compromise

An OSV / GHSA advisory, or a package plus a semver range. Firestop expands that into the set of affected Release.key values already in the graph.

02

Compute blast radius

One multi-source call asks: every service → every compromised release. That is HydraDB’s algo.MSpaths — not a hand-rolled BFS that times out on a real graph.

03

Show the paths

Each chain crosses lockfile, pin, and dependency edges — npm, yarn, and pnpm alike — so you see how the bad release gets in, not just that something is exposed.

04

Seal the chokepoints

A min hitting-set over path hops picks the fewest bumps that cut every live path, then verifies upgrades still do not reach the compromise.

05

Scrub time

DEPENDS_ON edges carry valid_from / valid_to windows. As-of filtering answers who resolved the bad version while it was live.

Under the hood

Why HydraDB is the product

algo.MSpaths

Multi-source, multi-target path enumeration in one procedure. Config is inline literals; selectors are string lists on key / name. Hub packages negotiate depth down when the frontier would exhaust the node.

Temporal DEPENDS_ON

Ranges like ^1.2.0 resolve differently by install time. Firestop stores validity windows and filters client-side after paths return — procedures cannot predicate on edge properties.

MinIO + indexer

Durable graph state lives in object storage. The indexer builds immutable CSC generations so multi-hop stays fast. Local filesystem backends cannot CAS the indexer cursor — MinIO is required.
